the problem

Reading the news is scattered across a dozen tabs.

Too many sources, no synthesis

Following several outlets means juggling tabs, apps, and newsletters — with no single place that pulls it together, summarizes it, and lets you filter to what you actually care about.

how it works

  1. Sources are registered

    An admin adds RSS feeds with a category and source name.

  2. Ingestion runs

    Each source is fetched and parsed asynchronously, with per-article fault isolation so one bad item never fails a whole batch.

  3. Content is cleaned & summarized

    HTML is stripped, and substantial articles are sent to Groq for a 3-point AI summary.

  4. Readers get a tailored feed

    Search, filter by category, follow sources, bookmark, and build a personalized "For You" feed.

under the hood

The stack

Chosen deliberately, not just "what I already knew."

Frontend

  • HTML / CSS — hand-built, no framework
  • Vanilla JavaScript — fetch-based API layer
  • In-memory token handling, no localStorage
  • Responsive, mobile-first layouts

Backend

  • Java 17 / Spring Boot
  • Spring Security + OAuth2 Client
  • Spring Data JPA, Spring Mail
  • jjwt for JWT signing/verification

AI

  • Groq API — LLaMA 3.1 8B Instant
  • Prompt engineered against hedging/filler output
  • Content-length gating before any API call

Database

  • MySQL — primary data store
  • JPA/Hibernate entity mapping
  • H2 in-memory DB for integration tests

Redis

  • Feed & article response caching
  • Login/OTP/registration rate limiting
  • One-time OAuth handoff codes

Other

  • Jsoup — RSS/HTML content cleaning
  • XXE-hardened DOM XML parser
  • JUnit 5, Mockito, AssertJ, MockMvc
  • Maven, GitHub Pages, Render

security

Hardened across multiple passes

Not a single audit at the end — security was revisited repeatedly as the project grew.

In-memory access tokens

Never written to localStorage — gone the moment the tab closes, closing the XSS token-theft window.

httpOnly sliding refresh cookie

Session extends with activity without ever exposing the refresh token to JavaScript.

One-time OAuth handoff codes

Google/GitHub login never puts a raw JWT in a URL, browser history, or server log.

XXE-hardened XML parsing

RSS ingestion blocks external entity resolution — no local file disclosure from a malicious feed.

Redis-backed rate limiting

Login, OTP, and password-reset endpoints are throttled, with failure-only counting so real users are never penalized.

Hashed refresh tokens at rest

SHA-256 hashed in the database — a DB leak alone can't hijack a session.

Enumeration-safe auth errors

Login and forgot-password responses never reveal whether an account exists.

Validated input everywhere

Bean Validation on every auth request, plus per-article fault isolation during ingestion.

honesty

What this is — and isn't — yet

A working project with a real feature set, built by one developer. Here's where it's genuinely limited.

Current limitations

  • No dedicated full-article reading page yet — articles are read via an AI-summary modal, not an in-app original-text view.
  • No user profile/settings page — account details can't be edited after registration.
  • Background RSS fetching is manually triggered in production (by design, to protect the free-tier AI API quota) rather than running on a timer.
  • Single admin role — no granular permission tiers.
  • Hosted on free tiers, so the first request after idle time may be slow to respond.
